# 面试讲解稿：怎么把这个技能讲出去

> 用途：面试官问「你有没有自己写过 skill / 做过 AI 工作流」时的完整打法。
> 原则：先讲问题，再讲设计，最后给证据。不要一上来罗列文件。

## 一、90 秒电梯版（背下来）

「我给自己做了一个面试复盘技能，装在我平时用的 AI 客户端里。

问题是：面完一场，我只有两种模糊感受——好像还行，和刚才那题不知道该怎么答。这种感受没法积累，同一类坑我会反复踩。

所以我把它拆成三层。第一层是**事实**：题量、每题耗时、结果有没有数字、有没有 STAR 结构、模糊词用了几个、JD 关键词覆盖了多少——这些全部由一个零依赖的 Node 脚本算，不让模型估。第二层是**判断**：五个维度打 1 到 5 分，每一分必须挂一句我的原话作为证据，脚本会去原始记录里核对这句话是不是真的存在，编不出来。第三层是**行动**：每条短板必须有动作、产出物、验收标准和截止时间，光写"多练习"直接校验不过。

跑完一场，我拿到一份 md：评分卡、逐题复盘、面试官下一层会追问什么、最丢分的三题怎么改写、以及我该补什么。多跑几场之后还能看趋势——比如我的技术纵深连续三场都是最低分，那就说明不是运气问题，是准备方式错了。

这套东西的价值不在提示词写得好，而在于我把**能算的东西从模型手里拿走了**：分数可复现，跨场能比较，建议可验收。」

## 二、3 分钟技术深挖版（讲架构与取舍）

1. **触发与上下文成本**：写成 DSH 技能（SKILL.md 约 100 行，只放流程），领域知识放 references/ 按需读，避免每次触发都灌几千字。
2. **计算层**：analyze.mjs 负责解析与测量——说话人标签识别（兼容"面试官：/我："、Q/A、加粗 markdown、带时间戳的转写）、连续同角色回合合并、问-答配对、每题指标（CJK 字数、按语速估算时长、带单位数字识别、STAR 信号、模糊词表、我们/我 主语比例、技术术语命中）。零依赖、纯 ESM、CLI 与库双形态（导出了纯函数，自检直接 import 来断言，不起子进程）。
3. **聚合层**：score.mjs 做三件事——schema 校验（五维齐全、分数 1-5、证据 >= 8 字、gap code 合法、动作四要素齐全）、加权与等级（权重来自公司性质档案，八类公司各有权重，和恒为 1.0）、历史追加与趋势（JSONL 存储，输出维度均值、首末对比、重复 gap 的连续场次）。
4. **一个具体取舍**：为什么不直接用模型抽指标？因为同一份记录抽两次结果不一样，跨场趋势就失去意义；正则和计数虽然朴素，但它可复现——今天 2.30 分，明天重跑还是 2.30 分。
5. **对抗幻觉**：证据回溯。每条 evidence 做空白归一化后必须能在原文里找到，找不到就告警，严格模式直接失败。
6. **验证方式**：selftest.mjs 28 项断言，覆盖解析器边界、指标计算、加权算术、等级边界、schema 负例、趋势聚合。改一行逻辑先跑测试。

## 三、面试官可能追问的 10 个问题

| 追问 | 怎么答 |
| --- | --- |
| 这不就是个大号提示词吗？ | 提示词只占第一层。真正的差别是计算层和校验层：脚本负责可复现的测量与算术，schema 负责拒绝空话，提示词只负责判断。 |
| 你怎么保证模型不胡说？ | 两道闸门：证据必须能在原文里字面匹配（空白归一化后）；维度分与归因 code 受枚举约束，非法值直接非零退出。 |
| 评测过效果吗？ | 事实层用固定样例做回归（28 项断言，含负例）；判断层的锚点写死了 1/3/5 分长什么样，并用"同一场记录两次独立打分"检查稳定性。 |
| 失败案例有哪些？ | ①记录太稀疏（只有零星回忆）→ 进入降级模式，指标只做定性，且禁止伪造时长；②说话人标签混乱 → 解析器告警 + --speaker-map 显式指定；③口音重的语音转写错误 → 关键词识别偏差，靠覆盖率而非逐字判分。 |
| 为什么用 Node 不用 Python？ | 零依赖、跨平台、安装即用；DSH 技能体系本身就是 Node 生态，脚本可以被技能直接调用。 |
| 权重是怎么定的？ | 按公司性质给了八套档案（大厂重纵深、国企重稳定与表达、外企重结构化），每套和必须为 1.0；权重只影响总分与短板优先级，不给人贴标签。 |
| 数据隐私怎么办？ | 全本地计算，产物写到工作目录的 retro/ 并进 .gitignore，原始记录不上传。 |
| 这套东西能迁移到别处吗？ | 能。"脚本测事实 + 模型做判断 + schema 做闸门"这套模式适用于任何需要跨次数对比的 AI 工作流，比如周报质量评估、代码评审复盘、客服会话质检。 |
| 你觉得它最大的风险是什么？ | 过度依赖指标：量化率上去了不代表讲得对。所以 rubric 里"事实与量化"只占一维，纵深与匹配是独立维度，且报告要求分数之间不一致时必须解释。 |
| 为什么不做成网页/插件？ | 先做最小可用闭环，验证"复盘真的会改变下一次表现"。形态是最后一步，现在一条命令就能跑通全链路。 |

## 四、现场演示脚本（3 分钟，全程可复现）

1. 打开 examples/sample-transcript.md：「这是一场脱敏的转写记录，12 题。」
2. 跑 analyze：
   node skills/interview-retro/scripts/analyze.mjs examples/sample-transcript.md --jd examples/sample-jd.md --company "互联网大厂"
   → 指着输出说：量化率 8%、我们 17 次比我 6 次、JD 覆盖 31%、风险题排第一的是服务拆分那题（7 个信号）。
3. 故意改坏一个分数（把 evidence 改成一个不在原文里的句子），再跑 score：
   → 展示校验失败与"这条证据在原始记录里找不到"，说明闸门是真的会拦人的。
4. 改回正确值，跑 score + trend：
   → 加权 2.30 / C 级；再跑 trend-demo 展示三场趋势（G3 连续三场）。
5. 收尾：打开 sample-report.md 的"补齐计划"表，指出每条都有产出物和验收标准——「这份报告不是感想，是任务单。」

## 五、一句话收口

「面试复盘这件事，最怕的是把'感觉还行'当成结论。我做的这个技能，就是把感觉拆成可测量的指标、可追溯的证据和可验收的动作——它不替我做决定，但它让我每一次复盘都比上一次更具体。」

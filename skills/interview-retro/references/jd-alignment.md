# JD 关注点提取与对齐改写

JD 不是关键词清单，而是**对方缺什么人的画像**。同一句话写在「岗位职责」和「任职要求」里的权重完全不同。

## 一、三列拆解

| 列 | 从 JD 的哪里抽 | 用途 |
| --- | --- | --- |
| 硬技能 | 任职要求里的名词（技术栈、工具、方法论） | 决定 analysis 的 jd.coverage，逐条找证据 |
| 业务语境 | 岗位职责里的场景（高并发交易、数据平台、政企交付） | 决定你的经历怎么翻译 |
| 软性要求 | 「推动」「跨团队」「owner 意识」「抗压」 | 决定行为题的素材选择 |

## 二、提取规则

1. 按出现次数与位置排序：出现 >=2 次或写在第一条的要求 = 核心要求。
2. 区分「熟悉」与「精通」：熟悉只需能讲清原理与一次实践；精通要有取舍、失败与优化数据。
3. 抓「优先」后面的内容：那是加分项，通常也是面试官最想问的差异化问题。
4. 业务语境词（例如「实时」「离线」「成本」「合规」「多租户」）要单独列出，用来改写项目标题。

## 三、对齐改写三例

- 原文：负责订单系统的性能优化。
- JD 要的是「高并发 + 稳定性」→ 改写成：在峰值 8000 QPS 下把下单链路 P99 从 800ms 压到 320ms，并补齐限流降级，避免了大促期间的雪崩。
- JD 要的是「成本」→ 改写成：通过读写分离与冷热数据分层，把该系统的数据库成本从每月 X 降到 Y，同时保持 P99 不变。
- JD 要的是「跨团队推动」→ 改写成：推动交易、风控、客服三方统一了超时与补偿口径，把资损类问题从每月 N 起降到 0。

原则：**同一段经历，按 JD 的关注点换口径讲**，而不是换事实。

## 四、覆盖率怎么用

analysis.json 的 jd.coverage 是「JD 关键词在候选人回答里出现的比例」，它只说明「有没有提」，不代表「讲透了」。使用时：

- coverage < 0.4：大概率匹配错位（G4），优先修口径。
- 0.4 - 0.7：核心技能命中，但加分项缺失，补 1-2 个关键词背后的实践。
- > 0.7：匹配没问题，把精力放到纵深与量化。
- 警惕反向风险：为了刷覆盖率硬塞名词，会立刻被追问打穿。

## 五、缺证据时怎么办

对每个核心要求标注证据强度：

| 强度 | 判定 | 处理 |
| --- | --- | --- |
| A 有数据 | 能给出规模、结果、代价 | 直接作为主力案例 |
| B 有经历 | 做过但没量化 | 补口径与对照数据，标 [待补数据] |
| C 只有了解 | 读过文档、看过别人做 | 只能答原理与判断，禁止包装成实战 |
| D 完全没有 | 没接触过 | 换同构案例，或列入「临时补一块最小实践」 |

禁止把 C 讲成 A —— 这是面试中最常见的翻车原因。

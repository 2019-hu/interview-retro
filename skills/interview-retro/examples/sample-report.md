## 4. 逐题复盘

### Q1：先做个自我介绍吧

- 面试官真实意图：不是听履历，而是看你**如何选择讲什么**——自我定位、信息组织、以及有没有一件「非你不可」的事。
- 我的回答要点：四年后端、订单团队、Java + Spring + Redis + Kafka、团队做过优化与拆分、日常写需求改 bug 参加评审。
- 丢分点（原话证据）：「反正比较熟悉这块业务」——用一句模糊词收尾；全文「我们」出现 17 次，「我」只有 6 次，没有任何个人独有动作。
- 追问预测 L1：你在这个订单系统里，最不能被别人替代的一件事是什么？
- 追问预测 L2：如果把你换掉，团队会立刻缺哪块能力？
- 改写骨架：定位句（做交易链路的 4 年后端）→ 一条主线案例（订单创建链路，峰值 X QPS）→ 一个只有我做的动作（推动三方统一超时与补偿口径）→ 与岗位对接（贵岗的稳定性/容量方向我做过一半）。

### Q2：你说的订单系统，QPS 大概多少

- 面试官真实意图：验证规模真实性，同时看你对自家系统数据是否敏感。
- 我的回答要点：平时 2000 左右，大促可能 8000，「没太注意具体数字」。
- 丢分点（原话证据）：「差不多平时 2000 左右吧」——一句里有「差不多/左右」两个模糊词；且没说均值还是峰值、数据来自监控还是压测。
- 追问预测 L1：这个 2000 是监控均值还是压测值？峰值持续多久？
- 追问预测 L2：峰值 8000 时哪个资源先到瓶颈？你怎么知道的？
- 改写骨架：日常均值 X QPS（7 日均值，取自监控）→ 大促峰值 Y QPS（持续约 Z 分钟）→ 当时瓶颈在数据库连接池，依据是监控面板哪两条曲线。

### Q3：这个量级下，你做过哪些具体优化

- 面试官真实意图：能否把优化讲成因果链，而不是罗列动作。
- 我的回答要点：库存扣减异步化（Kafka 削峰）+ Redis 缓存热点 + SQL 优化，结果「快了不少、投诉下降」。
- 丢分点（原话证据）：「中间其实也踩过挺多坑的，大致就是缓存和数据库不一致之类的问题，后来慢慢都解决了」——三个动作无优先级、无归因、无数字，踩坑被一句话糊掉。
- 追问预测 L1：这三件事各自贡献多少收益？怎么区分归因？
- 追问预测 L2：只允许做一件事，你砍掉哪个？为什么？
- 改写骨架：先给瓶颈定位（P99 从 X→Y 的监控曲线）→ 三个动作各自的收益与代价 → 一次真实踩坑（现象/定位/修复）→ 事后防复发（压测 + 告警阈值）。

### Q8：你刚才说做过服务拆分，具体怎么拆的

- 面试官真实意图：确认你是否真的主导过拆分，以及是否理解跨服务一致性（这是 JD 第 4 条）。
- 我的回答要点：订单拆成订单 + 库存，改用 RPC 并配超时重试，一致性用本地消息表 + 定时补偿。
- 丢分点（原话证据）：「上线之后整体还行，没有什么大问题」——拆分前后零数据；把最关键的风险点一句话带过。本题是全场风险分最高的一题（11 分，命中 7 个信号）。
- 追问预测 L1：拆完之后错误率有变化吗？超时重试带来的重复调用怎么处理？
- 追问预测 L2：本地消息表补偿一直失败，业务上怎么兜底？有没有人工介入流程？
- 改写骨架：拆分动机（当时痛点 + 数据）→ 边界划分原则 → 一致性方案对比（本地消息表 vs 事务消息 vs TCC 的代价）→ 上线后观测数据（延迟/错误率/故障数）。

### Q10：团队之间如果有分歧，你怎么处理

- 面试官真实意图：行为题，看影响力与推动方式，不是看脾气好不好。
- 我的回答要点：尊重大家意见，有分歧找 leader 拍板，团队氛围重要。
- 丢分点（原话证据）：「如果实在有分歧就找 leader 拍板」——把决策权直接交出去，等于承认没有推动力；且没有具体案例。
- 追问预测 L1：举一个你靠数据说服别人的例子，对方一开始反对什么？
- 追问预测 L2：如果 leader 拍板支持了你的对手，你会怎么做？
- 改写骨架：一次真实分歧（方案 A vs B）→ 双方论据 → 我用什么数据/实验推进 → 结果 → 事后关系维护。

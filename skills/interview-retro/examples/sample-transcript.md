# 面试记录（脱敏样例）— 某互联网公司 · 后端开发工程师 · 一面

[00:00:10] 面试官：先做个自我介绍吧。
[00:00:20] 我：面试官好，我是 XXX，做了四年后端，主要在我们公司的订单团队。我们团队负责订单创建、库存扣减这些核心链路，我们平时用 Java 和 Spring，中间件主要是 Redis 和 Kafka。我们做过挺多优化的，比如说性能优化、稳定性建设，我们团队这两年一直在做服务拆分。我个人日常就是写需求、改 bug、参加评审，反正比较熟悉这块业务。
[00:02:40] 面试官：你说的订单系统，QPS 大概多少？
[00:02:50] 我：我们那个系统差不多平时 2000 左右吧，大促的时候会高一些，可能能到 8000。不过我没太注意具体数字，应该是这么个量级。
[00:04:00] 面试官：这个量级下，你做过哪些具体优化？
[00:04:10] 我：当时下单接口的响应时间比较慢，我做了几件事。第一是把库存扣减从同步改成异步，用 Kafka 削峰；第二是加了 Redis 缓存，热点商品走缓存；第三是优化了 SQL。最后效果还不错，接口快了不少，用户投诉也下降了。中间其实也踩过挺多坑的，大致就是缓存和数据库不一致之类的问题，后来慢慢都解决了。
[00:06:30] 面试官：为什么用 Kafka 削峰，而不是其他方案？
[00:06:40] 我：因为 Kafka 是主流方案，大家做削峰都用它，而且它吞吐量高、支持持久化，社区也活跃，所以我们选它。
[00:07:20] 面试官：那如果不用 MQ，直接在应用层做队列和批量提交，你觉得可行吗？
[00:07:30] 我：应该也可以吧，不过 Kafka 更成熟一些。
[00:08:00] 面试官：缓存和数据库不一致的问题，你们最后怎么处理的？
[00:08:10] 我：这块我们讨论过几种方案。最直接的是先更新数据库再删缓存，但是会有并发窗口，如果读请求在删缓存之后、更新数据库之前进来，还是会拿到旧数据，所以我们加了延迟双删，把第二次删除推迟 500ms。我们也评估过订阅 binlog 异步删缓存的方案，代价是要引入额外的组件和运维成本，考虑到我们团队人手有限，最后没有上。业务上我们对一致性要求是最终一致，允许秒级延迟，所以这个方案是够用的。
[00:11:20] 面试官：有没有遇到过线上故障？
[00:11:30] 我：好像没有特别严重的，我们线上一直挺稳定的。
[00:11:50] 面试官：你刚才说做过服务拆分，具体怎么拆的？
[00:12:00] 我：我们把订单服务拆了，拆成订单和库存两个服务。拆完之后接口调用变成 RPC 了，我们用了公司的 RPC 框架，配了超时和重试。拆分过程中主要是数据一致性的问题，有些原来在一个事务里的操作跨服务了，我们改成用本地消息表加定时补偿。上线之后整体还行，没有什么大问题。
[00:15:00] 面试官：本地消息表的消息积压了怎么处理？怎么保证幂等？
[00:15:10] 我：积压的话可以扩容消费者，或者优化消费逻辑。幂等我们是根据消息里的业务 ID 做去重的，用一个表记录处理过的 ID，处理前先查一下。
[00:17:00] 面试官：团队之间如果有分歧，你怎么处理？
[00:17:10] 我：我一般会比较尊重大家的意见，先听别人怎么说，如果实在有分歧就找 leader 拍板。我觉得团队氛围比较重要，尽量不要因为技术问题伤和气。
[00:19:00] 面试官：最后一个问题，你自己平时怎么做技术选型？
[00:19:10] 我：主要还是看团队熟悉什么，用大家熟悉的技术风险比较小，另外就是看社区活跃度，尽量选主流方案。
[00:21:00] 面试官：行，那今天就先到这里，你有什么想问我的吗？
[00:21:10] 我：暂时没有，谢谢面试官。
